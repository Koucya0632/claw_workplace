# 多 Agent 測試 Case 生成工具方案

## 1. 方案概述

本方案目標是建立一個可落地的 **多 Agent 測試 Case 生成工具**，協助使用者從需求文件、功能描述、畫面資訊中，自動完成以下工作：

- 需求拆解
- 畫面檢查（可選）
- 測試點設計
- 測試 Case 編寫
- 覆蓋率檢查
- 匯出標準化結果

此工具適合用於以下場景：

- App / Web 產品功能測試
- PRD / MD / User Story 轉測試案例
- 測試設計效率提升
- QA 團隊標準化測試案例輸出
- 快速建立回歸測試基礎資料

---

## 2. 建置目標

### 2.1 核心目標
輸入一份需求資料後，自動產出：

1. 結構化需求分析結果
2. 畫面元素與 UI 檢查點（可選）
3. 測試點清單
4. 標準化測試 Case
5. 匯出為 Markdown / CSV / Excel 格式

### 2.2 產品價值
- 降低人工撰寫測試案例成本
- 提升需求轉測試的速度
- 減少測試點遺漏
- 統一測試案例格式
- 支援後續擴充到 Jira / TestRail / Xray 等系統

---

## 3. 整體架構設計

建議將系統設計為一條 **結構化產線**，而不是單純讓多個 Agent 自由對話。

整體流程如下：

```text
使用者輸入需求
   ↓
需求分析 Agent
   ↓
(可選) 畫面檢查 Agent
   ↓
測試設計 Agent
   ↓
測試 Case 編寫 Agent
   ↓
測試覆蓋校驗 Agent
   ↓
輸出整理 Agent
   ↓
輸出 Markdown / CSV / Excel
```

---

## 4. Agent 分工設計

## 4.1 需求分析 Agent

### 角色定位
負責讀取需求文件，將自然語言需求轉為結構化需求資料。

### 主要職責
- 解析 PRD / MD / User Story / 功能說明
- 拆解功能模組
- 抽取前置條件
- 拆解主流程 / 分支流程 / 異常流程
- 整理驗證規則與限制條件
- 標記待確認項目

### 輸入
- PRD 文件
- Markdown 需求文件
- 純文字需求描述
- API 規格補充

### 輸出範例
```json
{
  "feature_name": "登入",
  "modules": [
    {
      "name": "帳號密碼登入",
      "preconditions": ["使用者已註冊"],
      "main_flow": ["輸入帳號", "輸入密碼", "點擊登入"],
      "validations": ["帳號不可為空", "密碼不可為空"],
      "exceptions": ["網路異常", "帳號不存在", "帳號被停用"]
    }
  ],
  "open_questions": ["密碼輸入錯誤是否有限制次數？"]
}
```

---

## 4.2 畫面檢查 Agent（可選）

### 角色定位
負責根據畫面截圖、Figma 匯出圖或頁面描述，補足 UI 層測試資訊。

### 主要職責
- 盤點頁面元素
- 整理欄位、按鈕、文案、互動控件
- 補充 UI 顯示與互動檢查點
- 標記與需求不一致處

### 適用場景
- 表單頁面較多
- UI 驅動型功能
- 需要驗證欄位、按鈕、提示、版面

### 輸出範例
```json
{
  "page_name": "登入頁",
  "ui_elements": [
    {"type": "input", "name": "帳號輸入框"},
    {"type": "input", "name": "密碼輸入框"},
    {"type": "button", "name": "登入按鈕"},
    {"type": "link", "name": "忘記密碼"}
  ],
  "ui_checks": [
    "密碼輸入框需遮罩",
    "登入按鈕在未輸入時不可點擊",
    "錯誤提示文案需顯示在輸入框下方"
  ]
}
```

---

## 4.3 測試設計 Agent

### 角色定位
負責將需求轉為完整測試點，是整個工具的核心 Agent。

### 主要職責
- 依功能點建立測試點矩陣
- 補足測試維度
- 從 QA 視角檢查需求風險
- 區分不同類型測試點

### 必須覆蓋的測試維度
- 正向流程
- 反向流程
- 邊界值
- 欄位驗證
- 權限與角色
- 狀態流轉
- 異常情境
- 網路異常
- 重複操作
- 相容性
- 資料一致性

### 輸出範例
```json
{
  "feature_name": "登入",
  "test_points": [
    {"category": "功能", "point": "使用正確帳號密碼可成功登入"},
    {"category": "驗證", "point": "帳號為空時提示必填"},
    {"category": "驗證", "point": "密碼為空時提示必填"},
    {"category": "異常", "point": "網路中斷時登入失敗並提示"},
    {"category": "安全", "point": "密碼輸入需遮罩"}
  ]
}
```

---

## 4.4 測試 Case 編寫 Agent

### 角色定位
將測試點轉為標準化、可執行的測試案例。

### 主要職責
- 根據測試點產出測試案例
- 補齊前置條件
- 拆解具體操作步驟
- 明確定義可驗證的預期結果
- 標記優先級與類型

### 建議輸出欄位
- 功能名稱
- 模組
- 測試標題
- 測試目標
- 前置條件
- 測試步驟
- 預期結果
- 優先級
- 類型
- 備註

### 輸出範例
```json
{
  "feature_name": "登入",
  "cases": [
    {
      "module": "帳號密碼登入",
      "title": "使用正確帳號密碼登入成功",
      "objective": "驗證有效帳號密碼可正常登入",
      "preconditions": ["使用者已註冊有效帳號"],
      "steps": [
        "開啟登入頁",
        "輸入正確帳號",
        "輸入正確密碼",
        "點擊登入按鈕"
      ],
      "expected": [
        "登入成功",
        "跳轉首頁",
        "顯示使用者登入狀態"
      ],
      "priority": "P0",
      "type": "正向"
    }
  ]
}
```

---

## 4.5 測試覆蓋校驗 Agent

### 角色定位
從 QA Lead 角度檢查整體測試案例是否完整。

### 主要職責
- 檢查是否遺漏異常流程
- 檢查是否缺少邊界值案例
- 檢查是否遺漏權限與狀態流轉
- 檢查是否存在重複案例
- 指出描述過於模糊的案例
- 補充風險提醒

### 輸出範例
```json
{
  "coverage_report": {
    "missing_areas": [
      "缺少帳號鎖定場景",
      "缺少弱網重試場景"
    ],
    "duplicate_cases": [
      "登入失敗提示文案相關案例有重複"
    ],
    "quality_issues": [
      "部分預期結果使用『系統正常』，不可驗證"
    ]
  }
}
```

---

## 4.6 輸出整理 Agent

### 角色定位
將最終結果整理為目標格式，方便使用者直接下載或導入其他系統。

### 主要職責
- 格式轉換
- 欄位對齊
- 去除不必要說明
- 支援多種輸出模板

### 支援格式
- Markdown
- CSV
- Excel
- 後續可擴充：TestRail、Jira、Xray 匯入格式

---

## 5. 建議的資料流模型

為避免多個 Agent 之間只靠自然語言傳遞資訊，建議採用統一的 JSON Schema 作為中介資料結構。

### 建議中介資料模型
```json
{
  "project": "會員系統",
  "feature": "登入",
  "requirements": [],
  "ui": [],
  "test_points": [],
  "test_cases": [],
  "coverage_report": {},
  "metadata": {
    "source_type": "markdown",
    "version": "v1"
  }
}
```

### 設計原則
- 每個 Agent 只負責補自己負責的欄位
- 上游輸出必須結構化
- 下游只讀取結構化結果
- 避免跨 Agent 任意修改其他模組內容

## 7. MVP 建議範圍

建議先做最小可行版本，不要一開始就做太重。

### MVP 功能
1. 需求分析 Agent
2. 測試設計 Agent
3. 測試 Case 編寫 Agent
4. 結果匯出 Markdown / CSV / Excel

### MVP 暫不處理
- 圖片畫面理解
- 自動比對 Figma
- Jira / TestRail 串接
- 自動生成 API 測試腳本
- 自動執行測試

### 原因
這樣可以先驗證核心價值：
**需求 → 測試點 → 測試案例**
是否真的能提升你的工作效率。

## 8. 技術方案建議

## 8.1 後端
建議使用：

- Python
- FastAPI

原因：
- 開發速度快
- 容易串接 LLM
- 容易輸出 Excel / CSV
- 適合 workflow 型應用

## 8.2 Agent 編排
可選方案：

### 方案 A：簡單函式式流程
- 每個 Agent 對應一個 service function
- 明確控制資料流
- 最適合 MVP

### 方案 B：LangGraph / 類似框架
- 適合後續擴充多分支流程
- 適合做重試、審核、條件分流

### 建議
第一版優先採用 **函式式流程**，先穩定，再決定是否升級。

## 8.3 LLM 使用建議
- 一個主模型即可
- 不必一開始就做多模型切換
- 重點在於角色 prompt 與輸出 schema 控制

## 8.4 輸出技術
- Markdown：原生字串輸出
- CSV：pandas
- Excel：openpyxl 或 pandas + openpyxl

## 10. Agent Prompt 設計原則

## 10.1 需求分析 Agent Prompt 原則
- 不直接寫測試案例
- 專注拆解需求
- 明確區分主流程、例外流程、規則、限制
- 不確定內容需標記待確認

## 10.2 畫面檢查 Agent Prompt 原則
- 只處理畫面元素與互動
- 不自行推測商業邏輯
- 需要區分「確定資訊」與「疑似資訊」

## 10.3 測試設計 Agent Prompt 原則
- 必須從多維度思考
- 不只產出正向案例
- 要主動補風險與異常情境
- 每個測試點需清楚標記類型

## 10.4 測試 Case 編寫 Agent Prompt 原則
- 步驟必須具體
- 預期結果必須可驗證
- 不可使用模糊表述
- 每個 Case 要能直接交給測試人員執行

## 10.5 覆蓋校驗 Agent Prompt 原則
- 以找漏為主
- 指出重複與低品質案例
- 給出補強建議

## 12. 系統風險與注意事項

## 12.1 需求本身不完整
若原始需求不完整，Agent 可能只能輸出部分測試案例，因此系統需保留：
- 待確認項目
- 假設條件
- 缺失資訊提醒

## 12.2 畫面檢查容易過度推測
若用圖片理解，需避免把畫面內容當成已確認的業務規則。

## 12.3 Case 容易數量很多但品質不高
因此一定要加入 **覆蓋校驗 Agent** 或至少加入品質檢查階段。

## 12.4 不同團隊的格式不同
輸出層必須模板化，避免後續修改成本過高。

## 14. 結論

此工具最適合被定位為：

> 一個輸入需求文件，自動拆解需求、設計測試點、生成標準化測試案例並匯出表格的多 Agent QA 工具。

### 核心成功關鍵
1. 不把 Agent 當作隨機聊天角色，而是明確分工的產線節點  
2. 每一層都使用結構化資料傳遞  
3. 先做 MVP，驗證需求轉測試案例的核心價值  
4. 後續再逐步擴充到畫面理解、覆蓋率評估與外部系統串接
