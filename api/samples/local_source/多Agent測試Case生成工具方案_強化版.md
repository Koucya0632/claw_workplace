# 多 Agent 測試 Case 生成工具方案（強化版）

> 目標：在原本「需求 → 測試點 → 測試 Case」產線式設計上，補強 **本地模型 Ollama + Qwen3:14B** 的落地細節，以及一套 **簡潔但步驟清楚、進度明確** 的 UI/UX 設計。

---

## 1. 方案定位升級

這個工具不只是「幫忙寫測試案例」，而是做成一個 **QA 測試設計工作台**：

- 輸入需求文件 / PRD / User Story / 畫面資訊
- 用多 Agent 流程完成分析、測試設計、Case 生成、覆蓋檢查
- 讓使用者看得到：
  - 現在做到哪一步
  - 哪一步需要人工確認
  - 哪一步是 AI 推測
  - 哪些輸出可以直接匯出

所以產品核心不是「聊天」，而是 **可視化流程 + 結構化結果 + 可追蹤進度**。

---

## 2. 建議的整體產品模式

建議做成 **左側流程、中央工作區、右側結果/風險區** 的三欄式工作台。

### 2.1 主要操作模式

#### 模式 A：快速生成
適合需求比較清楚時使用。

流程：
1. 貼入需求
2. 選擇是否啟用 UI 檢查
3. 點擊生成
4. 系統自動跑完整流程
5. 最後給出測試 Case + 覆蓋報告

#### 模式 B：分步生成
適合需求較複雜、想要人工介入時使用。

流程：
1. 先做需求分析
2. 人工確認需求拆解
3. 再做測試點設計
4. 人工確認測試點
5. 再生成測試 Case
6. 最後做覆蓋檢查與匯出

### 2.2 建議預設模式

預設使用 **分步生成**。

原因：
- 測試 Case 品質通常取決於前面需求拆解是否正確
- 讓使用者在中途確認，可大幅降低「後面生成一大堆但方向錯誤」的情況
- 比較符合 QA 真實工作流程

## 3. 本地模型方案設計（Ollama + Qwen3:14B）

原方案提到「一個主模型即可」，這個方向可以保留，但若要真的可用，建議補上以下設計。

### 3.1 為什麼 Qwen3:14B 適合這個場景

把本地模型放在 QA 工具裡，重點不是追求最大模型，而是要平衡：

- 中文能力
- 結構化輸出能力
- 指令遵循能力
- 成本可控
- 本地可部署
- 生成速度不能太慢

Qwen3 系列目前已可透過 Ollama 直接拉取，且提供 14B 規格；官方頁面也列出其屬於支援 thinking 的模型家族。citeturn642414search0turn642414search2

對你的工具來說，**Qwen3:14B 很適合作為主力模型**，因為：

- 比 7B 類模型更穩定，較適合需求拆解、測試點分類、表格化輸出
- 比 30B / 32B 更容易本地部署，硬體壓力低很多
- 中文與技術任務表現夠平衡，適合 PRD、功能說明、測試案例生成
- 支援 thinking / non-thinking 的使用方式，適合把「需求分析」和「Case 批量整理」拆成不同推理深度的任務。citeturn642414search1turn642414search3turn642414search5

### 3.2 本地模型角色分工建議

雖然可以只用一個模型，但**任務層要分級**，不要每一步都用同樣推理強度。

#### 任務分級

**L1：快速整理型任務**
- 文本清洗
- 標題整理
- 欄位格式補齊
- CSV / Markdown 欄位映射
- UI 標籤抽取

建議：Qwen3:14B non-thinking

**L2：結構分析型任務**
- 需求拆解
- 主流程 / 例外流程抽取
- 規則整理
- 測試點分類

建議：Qwen3:14B thinking

**L3：品質審查型任務**
- 覆蓋率檢查
- 漏測風險檢查
- 重複案例檢查
- 步驟與預期結果可驗證性審查

建議：Qwen3:14B thinking

### 3.3 本地部署建議架構

```text
Frontend (React / Next.js)
    ↓
Backend API (FastAPI)
    ↓
Workflow Orchestrator
    ├─ Requirement Agent
    ├─ UI Inspector Agent
    ├─ Test Design Agent
    ├─ Test Case Writer Agent
    ├─ Coverage Reviewer Agent
    ↓
LLM Gateway
    ↓
Ollama
    └─ qwen3:14b
```

### 3.4 不要讓前端直接打 Ollama

建議一定要加一層 **LLM Gateway / Model Service**，不要讓前端直接呼叫 Ollama。

原因：
- 可以統一 prompt 模板
- 可以控制 timeout / retry
- 可以限制最大輸出長度
- 可以記錄每一步耗時
- 後續想替換模型比較容易
- 比較方便做審計與除錯

### 3.5 模型調用策略

#### 建議策略
- 每個 Agent 固定一份 prompt 模板
- 每個 Agent 固定輸出 schema
- 每一步先驗證 JSON，失敗才重試
- 不要讓下游直接吃自然語言

#### 建議重試機制
- 第 1 次：正常生成
- 第 2 次：加強 schema 提示
- 第 3 次：降級輸出為半結構化，再由 parser 修復

### 3.6 本地模型常見風險

#### 風險 1：輸出格式不穩
解法：
- 嚴格 schema
- JSON parser + repair
- case writer 與 export formatter 分離

#### 風險 2：長文件容易掉資訊
解法：
- 先 chunk 再 summarize
- Requirement Agent 先做分段需求抽取
- 最後做全局 merge

#### 風險 3：測試 Case 量一多就開始重複
解法：
- 先產測試點，再由 case writer 逐批生成
- 用 hash / embedding 做重複檢查
- Coverage Reviewer 單獨做去重與補漏

#### 風險 4：本地機器速度不穩
解法：
- 前端顯示步驟級進度，而不是假裝即時秒出
- 長任務採分段生成
- 支援「先看需求分析結果，再繼續」

## 4. 建議的 Agent 強化分工

原本 5 個 Agent 方向是對的，但我建議補成 **6 個職責層**，讓 UI 與工程也更好對應。

### 4.1 Document Intake Agent

新增一層在最前面，先做輸入標準化。

職責：
- 辨識輸入來源（PRD / MD / 純文字 / 截圖）
- 清洗格式
- 切段
- 抽標題層級
- 建立段落 ID

這一層做完，後面 Agent 才不會直接面對混亂原文。

### 4.2 Requirement Analysis Agent

保留原本定位，但輸出要加：
- requirement_id
- source_paragraph_ref
- confidence
- open_question

### 4.3 UI Inspection Agent（可選）

建議不要直接用來判定商業邏輯，只做：
- 元件盤點
- 欄位 / 按鈕 / 提示文案抽取
- 互動路徑補充
- 與需求對照差異提示

### 4.4 Test Design Agent

除了列測試點，建議多輸出：
- 風險等級
- 測試類型
- 對應需求 ID
- 是否建議人工補充

### 4.5 Test Case Writer Agent

建議採 **一個測試點 → 一組候選 Case** 的模式，不要一次全量暴衝。

### 4.6 Coverage Reviewer Agent

重點不是只說「漏了什麼」，而是要給：
- 漏測分類
- 建議新增案例數
- 重複率
- 模糊描述數量

### 4.7 Export Formatter Agent

不是 AI Agent 也可以，很多內容可以直接程式化處理。

建議這層盡量少用 LLM，避免：
- 表格欄位飄掉
- 步驟格式被改寫
- 匯出時內容不穩

## 5. UI/UX 設計方向（簡潔但步驟明確）

你要的 UI/UX 核心不是「華麗」，而是：

- 一眼知道現在進度
- 一眼知道下一步要做什麼
- 一眼知道哪裡需要人確認
- 一眼知道哪些是 AI 推測

所以整體設計建議走：

**極簡工作台 + 分步流程 + 結果對照檢視**

### 5.1 整體頁面架構

```text
┌─────────────────────────────────────────────────────────────┐
│ Top Bar：專案名稱 / 模型狀態 / 匯出 / 歷史版本              │
├──────────────┬──────────────────────────────┬──────────────┤
│ 左側流程區    │ 中央工作區                     │ 右側摘要區    │
│ Stepper      │ 目前步驟的輸入 / 輸出內容         │ 進度 / 風險   │
│ 1~6 steps    │ 可編輯、可確認、可重跑           │ 覆蓋率 / 提示 │
├──────────────┴──────────────────────────────┴──────────────┤
│ Bottom Bar：執行狀態 / token估算 / 耗時 / 上一步 / 下一步    │
└─────────────────────────────────────────────────────────────┘
```

## 6. 主要頁面設計

### 6.1 首頁 / 新建任務頁

#### 目的
讓使用者快速開始一個測試生成任務。

#### 區塊
1. 輸入方式卡片
   - 貼上需求文字
   - 上傳 Markdown / PRD
   - 上傳截圖（可選）

2. 配置卡片
   - 模式：快速生成 / 分步生成
   - 模型：qwen3:14b
   - 是否啟用 UI 檢查
   - 輸出格式：Markdown / CSV / Excel

3. 啟動按鈕
   - 開始分析

#### UX 要點
- 一屏內完成，不要很多設定
- 預設值先幫使用者選好
- 高級設定摺疊起來

---

### 6.2 任務流程頁（核心頁）

這頁是整個產品重點。

#### 左側：步驟導航 Stepper

建議 6 步：
1. 輸入需求
2. 需求分析
3. UI 檢查（可跳過）
4. 測試點設計
5. 測試 Case 生成
6. 覆蓋檢查與匯出

每一步顯示 4 種狀態：
- 未開始
- 進行中
- 待確認
- 已完成

#### 中央：工作內容區

依當前步驟切換內容：

- 需求分析頁：顯示功能模組、流程、規則、待確認問題
- UI 檢查頁：顯示頁面元素、按鈕、欄位、提示文案
- 測試點頁：顯示分類後的測試點
- 測試 Case 頁：表格化顯示案例
- 覆蓋頁：顯示缺漏、重複、風險

#### 右側：摘要與進度區

固定顯示：
- 當前步驟進度
- 已抽出需求數
- 已生成測試點數
- 已生成案例數
- 待確認項目數
- 風險提示數

## 7. 進度設計（這部分很重要）

你特別提到要「明確步驟與進度」，所以不能只放一條假進度條。

建議使用 **兩層進度**。

### 7.1 第一層：流程總進度

例如：

- 需求分析 100%
- UI 檢查 100%
- 測試點設計 60%
- 測試 Case 生成 0%
- 覆蓋檢查 0%

使用者能知道現在卡在哪一層。

### 7.2 第二層：當前步驟內部進度

例如在「測試 Case 生成」這一步：

- 已完成 12 / 20 個測試點
- 已生成 48 條案例
- 重試 1 次
- 預估剩餘：8 個測試點

這種比單純的 loading 更有感，也比較像真正的工作流產品。

### 7.3 建議的進度文案

避免只顯示：
- Loading...
- AI is thinking...

改成：
- 正在拆解需求模組
- 正在整理主流程 / 例外流程
- 正在生成登入模組測試點（3/8）
- 正在檢查重複案例
- 正在整理 Excel 匯出欄位

## 8. 建議的 UI 元件清單

### 8.1 必備元件

- Stepper：流程步驟顯示
- Status Badge：未開始 / 進行中 / 待確認 / 完成
- Summary Card：需求數、案例數、風險數
- Diff Panel：原需求 vs AI 拆解結果
- Editable Table：測試點與測試案例編輯表格
- Issue Panel：待確認與風險提醒
- Export Drawer：匯出設定抽屜

### 8.2 推薦互動

#### A. 一鍵重跑單一步驟
例如只重跑「測試點設計」，不要整條流程重跑。

#### B. 人工確認後再下一步
這會讓工具更像 QA 助理，而不是黑盒生成器。

#### C. 折疊 AI 推測內容
把「AI 推測」「待確認」折疊在一個區塊，避免污染主結果。

#### D. 高亮來源對應
點一條需求時，右側高亮它對應的測試點與測試案例。

這個功能很重要，因為 QA 最常問的是：
**這個 Case 是根據哪條需求產生的？**

## 9. 建議的 UI 文案風格

建議走：
- 簡短
- 指令式
- 可操作
- 少形容詞

### 範例

不好：
- AI 正在為你智慧分析需求中...

較好：
- 正在分析需求結構
- 已抽取 6 個功能模組
- 發現 2 個待確認規則
- 請確認後繼續生成測試點

## 10. MVP 版 UI 頁面最小集合

如果你現在先做 MVP，頁面其實不用很多。

### MVP 只做 4 個頁面即可

1. 新建任務頁
2. 任務流程頁
3. 案例結果頁
4. 匯出頁 / 匯出彈窗

### MVP 暫時可以不做

- 歷史版本對比
- 多人協作
- Figma 雙欄比對
- 權限系統
- 自定義 Agent 編排器

## 11. 後端流程補強建議

### 11.1 任務狀態機

建議後端把每個任務做成狀態機：

```text
created
→ parsing
→ requirement_ready
→ ui_ready (optional)
→ test_points_ready
→ test_cases_ready
→ coverage_ready
→ exported
→ failed
```

### 11.2 每一步都要可追蹤

每步都記錄：
- step_name
- started_at
- finished_at
- duration_ms
- model_name
- retry_count
- output_count
- error_message

這樣前端才有東西可以做進度與診斷。

### 11.3 任務切分建議

不要整份需求一次全丟給 case writer。

建議切分粒度：
- 按功能模組
- 按測試點群組
- 按頁面

這樣 UI 也能顯示更細的進度。

## 12. Prompt / Schema 強化建議

### 12.1 每個 Agent 都要有固定 schema

例如 Requirement Agent：

```json
{
  "feature_name": "",
  "modules": [],
  "rules": [],
  "exceptions": [],
  "open_questions": [],
  "confidence": 0
}
```

### 12.2 加一個 confidence 欄位

原因：
- 可以在 UI 上標示「低信心」內容
- 幫助使用者優先檢查不穩定區塊

### 12.3 加一個 source_ref 欄位

原因：
- 可以回溯來源段落
- UI 更容易做對照檢視
- 有利於審核與除錯

## 15. 最後結論

在你原本方案基礎上，我最建議補強的不是再增加更多 Agent，而是補這三件事：

### 第一，補「本地模型落地策略」
不要只寫「用 Ollama + qwen3:14b」，而要明確定義：
- 哪些步驟用 thinking
- 哪些步驟用 non-thinking
- 哪些輸出走 schema 驗證
- 哪些流程允許重試

### 第二，補「工作流 UI」
這個產品如果只有輸入框 + 對話框，價值會大幅下降。
你真正需要的是：
- 步驟式工作流
- 可確認節點
- 可重跑單步
- 可視化進度
- 來源對照

### 第三，補「狀態機與追蹤」
這會直接決定你的 UI 能不能做好，也決定除錯效率。
