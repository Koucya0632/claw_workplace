# OpenClaw 開發準則

## 1. 文件目的與適用範圍

本文件是 OpenClaw 智能辦公室專案的正式開發準則。  
所有後續開發、重構、修錯、補測試、補文件，都必須先閱讀本文件，再開始動工。

本文件適用於：

- `web/` 前端程式
- `api/` 後端程式
- `api/app/tests` 與 `web` 測試檔
- `README.md`、`docs/`、方案相關文件

本文件的定位不是通用程式風格指南，而是本專案的落地開發規範。  
若本文件與個人習慣衝突，以本文件為準。  
若本文件與方案書衝突，以方案書的產品方向為準，再同步更新本文件。

## 2. 開發前必讀流程

每次開始新任務前，必須依序閱讀以下三份文件：

1. `OpenClaw_智能辦公室_整體方案書.md`
2. `docs/development-guidelines.md`
3. `README.md`

開始開發前，必須先確認以下事項：

- 本次任務屬於哪一個產品流程：搜索、整理、分析、輸出
- 本次修改會影響前端、後端、測試還是文件
- 本次任務是否與現有分層衝突
- 本次任務是否需要同步更新文件與測試

若任務需求不清楚，先補理解與規格，再寫代碼。  
禁止在沒有確認產品目的的情況下直接堆功能。

## 3. 專案開發核心原則

本專案所有代碼必須同時滿足以下四個原則：

- 可讀：別人第一次打開就看得懂
- 可管：模組邊界清楚，容易追蹤責任
- 可維護：後續修改不需要大面積拆毀
- 可測：關鍵邏輯可被驗證

以下行為視為違反本專案原則：

- 為了省時間把多個職責塞進單一檔案
- 在 router / page / component 中寫大量不可重用的業務邏輯
- 複製貼上相同邏輯而不抽共用
- 錯誤處理只回傳模糊訊息，導致無法排查
- 新增功能卻不補測試或不更新文件

## 4. 架構與模組拆分原則

### 4.1 單一職責

每個檔案只負責一種主要職責。  
每個模組只做自己那一層該做的事。

### 4.2 前後端分層

前端維持以下責任分工：

- `app/`：頁面入口與頁面級資料流
- `components/`：可重用 UI 元件
- `lib/`：型別、API client、共用工具

後端維持以下責任分工：

- `routers/`：API 入口、參數轉換、HTTP 錯誤回應
- `services/`：業務流程與任務編排
- `repositories/`：資料存取
- `providers/`：外部模型與第三方服務整合
- `connectors/`：資料源接入
- `schemas/`：輸入輸出資料模型

以下混寫禁止發生：

- router 直接寫大量資料庫操作
- repository 直接做流程判斷
- component 直接塞複雜業務規則
- page 檔案同時負責 UI、資料格式轉換、錯誤策略與共用邏輯

### 4.3 共用邏輯抽離

只要邏輯符合以下任一條件，就應優先抽離：

- 會被兩個以上頁面或模組重用
- 超過一個明顯責任
- 測試時需要獨立驗證
- 後續高機率會變動

## 5. 命名、目錄與檔案職責規範

命名必須清楚表達用途，不可使用模糊名稱。

允許：

- `search_service.py`
- `task_orchestrator.py`
- `source-status-board.tsx`

避免：

- `utils2.py`
- `temp.ts`
- `new-page.tsx`
- `test123.py`

新增檔案前必須先確認：

- 現有目錄是否已有合適位置
- 是否能沿用既有命名風格
- 是否會造成責任重疊

若一個檔案超過合理長度，或同時承擔多個責任，應主動拆分。  
禁止用「先寫完再說」作為長期結構理由。

## 6. 註解標準

本專案要求極高密度中文註解，標準為接近逐段逐行。  
目標不是把每個語法字面翻譯一遍，而是讓閱讀者快速理解這段代碼：

- 為什麼存在
- 正在做什麼
- 資料怎麼流動
- 錯誤怎麼處理
- 為什麼這樣寫而不是別種寫法

### 6.1 必須註解的內容

- 函式與方法的主要目的
- 條件分支的判斷理由
- 資料轉換邏輯
- 外部 API 請求與回應處理
- 錯誤處理與 fallback
- 非直觀的 UI 狀態切換
- 任務流程與角色協作邏輯

### 6.2 不可接受的註解方式

- 只把代碼字面重講一遍
- 註解比代碼還模糊
- 有複雜邏輯卻完全沒註解
- 註解和實際行為不一致

### 6.3 註解實務要求

- 優先用繁體中文
- 每段關鍵邏輯前都要有註解
- 複雜區塊內的重要步驟要有行內或段內註解
- 樣板、型別宣告、框架固定語法可減少機械式重複註解

## 7. 前端開發準則

前端必須維持 OpenClaw 的像素多角色工作台風格，不可任意偏離產品視覺方向。

前端開發必須遵守：

- 保持像素風、工作台、多角色、流程可視化的一致性
- 頁面應優先拆成可重用元件，不把所有畫面塞進單一 page
- API 呼叫集中在 `lib/api.ts` 類型的共用層
- 型別集中管理，不在多處重複手寫不同版本
- UI 錯誤、空狀態、載入狀態都要明確可見

以下做法禁止：

- 在頁面中散落硬編碼 API URL
- 元件同時兼做資料抓取、格式轉換、複雜業務規則
- 為了快而跳過錯誤提示與空狀態
- 新頁面完全脫離既有視覺語言

## 8. 後端開發準則

後端必須維持清楚的流程分層與可診斷性。

後端開發必須遵守：

- connector / provider / service / repository / router 分層清楚
- 所有外部 API 錯誤都要保留可診斷訊息
- schema 必須清楚定義輸入輸出
- 任務流程必須能追蹤狀態與錯誤
- 能抽象的外部整合，不直接寫死在流程裡

以下做法禁止：

- 在 router 直接拼接大量業務流程
- 在 service 層直接寫 SQL
- 只回傳 `failed`，卻不帶原因
- 把外部服務回應格式散落在多個檔案處理

## 9. 測試與驗證準則

新增或修改功能時，必須同步考慮驗證方式。  
若是正式功能改動，原則上要至少補一種可重複執行的驗證。

驗證方式包含：

- 單元測試
- API 測試
- 元件測試
- E2E smoke test
- build / type check / 啟動驗證

以下情況必須補測試或驗證：

- 新增 API
- 調整資料模型
- 修改摘要、搜索、任務編排等核心流程
- 修改共用元件或共用工具
- 修正已知 bug

若本次修改不適合補自動化測試，必須在文件或提交說明中寫清楚手動驗證方式。

## 10. 文件同步規範

文件是專案的一部分，不是最後才補的附屬品。

以下情況必須同步更新文件：

- 啟動方式改變
- 環境變數改變
- 專案結構改變
- 對外 API 或主要流程改變
- 新增團隊約定或開發規範

若修改已影響開發流程，卻沒有更新 `README` 或 `docs/`，視為未完成。

## 11. 禁止事項

本專案禁止以下做法：

- 未讀方案書與本文件就直接開始大改
- 把不同責任的邏輯混在同一層
- 留下臨時代碼、假名稱、無用途函式
- 新功能只做 happy path，不處理 error path
- 大量複製貼上後不抽離
- 提交看不懂、無註解、難維護的代碼
- 改了行為卻不補文件

## 12. 提交前檢查清單

每次提交前，至少自查以下項目：

- 我是否先閱讀方案書、開發準則、README
- 這次修改是否符合單一職責與分層原則
- 關鍵邏輯是否有高密度中文註解
- 錯誤處理是否可診斷
- 是否有可重複執行的驗證方式
- 是否需要更新 README 或 docs
- 是否留下臨時代碼、硬編碼或可抽離但未抽離的重複邏輯

若以上任一項答案是否定的，先修正，再提交。
